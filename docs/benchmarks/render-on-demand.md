# Render on demand

A world stops drawing frames when nothing on screen can change, and draws
again the moment something does. The update loop keeps running every frame
(controls, players, physics, audio, timers); only the draw is skipped.

-   Logic: `frontend/components/_3DExhibit-v2/three/utils/renderDemand.js`
    (pure decision, table-tested) and `utils/renderDemandGate.js` (what the
    engine feeds it). Wiring: `three/world3D.js` (`canSkipFrame`, `update`),
    `three/api.js` (frame timing, the room sharpening gate).
-   Off switch: `RENDER_ON_DEMAND` in `renderDemand.js`. With it `false`
    every frame is drawn and nothing is hooked.
-   Grace: frames keep drawing for 500 ms (`RENDER_DEMAND_GRACE_MS`) after
    the last change. Probe: while idle, one frame is drawn every 1000 ms
    (`RENDER_DEMAND_PROBE_MS`); if the GPU received anything new for it, the
    world is awake again.
-   Never skipped: the editor, the uploader, XR (`IS_VR` or `renderer.xr`
    enabled), recordings, `?stats`, `?cinematic`, an open dynamic portal, and
    every state but `IDLE`, `SPACE` and `EXPOSITION` (intro, transition,
    teleport, cinematic, panorama, exit).

## How change is seen

The engine has about fifty per-frame listeners and many more places that
animate something. Rather than mark each one (most live in files this
change does not own), the gate watches the few places every change has to
pass through:

| Signal                                                                                                                   | When it is read          | What it catches                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| GPU write meter: `backend.updateBinding`, `updateAttribute` (content compared), `updateTexture`, and the draw-call count | after every drawn frame  | anything that reached the GPU: uniforms changed in place, time uniforms, object and camera matrices, new or hidden objects, texture uploads |
| Camera: world matrix, projection, canvas size                                                                            | before a skip            | controls, inertia and damping, transitions, zoom, resize                                                                                    |
| Scene graph: every visible object's world matrix and material, the set of visible objects, background, environment       | before a skip            | players and avatars moving, bones of animated models, objects added, removed, shown or hidden, LOD swaps, material swaps                    |
| Per-frame listeners on `DAWN_UPDATE` … `PRE_RENDER`                                                                      | before a skip            | an animation starting (sprites, loaders, labels, lobby transitions subscribe when they start)                                               |
| gsap tweens in progress                                                                                                  | before a skip            | every gsap transition, fade and delayed call while it runs                                                                                  |
| Buffers marked for upload whose content the GPU does not have                                                            | before a skip            | instanced buffers changed by the update work                                                                                                |
| `Texture` / `Material` `needsUpdate = true` (prototype setters)                                                          | at once                  | video frames, canvas textures, loading, progressive upload, room sharpening                                                                 |
| A playing video texture's element, or any playing `<video>` in the page                                                  | every frame (continuous) | videos, HLS and video streams                                                                                                               |
| Pointer, touch, wheel, key, focus, tab visible; `setState`, resize, loop resumed                                         | at once                  | input, state changes                                                                                                                        |
| Room sharpening gate waiting for its verdict                                                                             | continuous               | keeps the first seconds measured as before                                                                                                  |

Rule when in doubt: draw. A frame is skipped only if no signal fired, no
continuous source is active, and the grace and probe intervals allow it.

### Not reliably detected, and what happens

-   A uniform changed in place by code that does not subscribe, tween, move
    anything or upload a texture, starting while the world is idle: seen by
    the next probe, at most 1 s late, then drawn every frame. Examples found:
    a morph-target-only model animation started without camera movement; a
    time-driven material coming into view through a move the scene graph
    does not show. None was found that runs on a timer alone.
-   A texture whose content changes without `needsUpdate` (an external GPU
    write): probe.
-   Anything that marks a texture or material for upload every frame, a
    gsap tween that never ends (including UI tweens on the page), a playing
    `<video>` anywhere in the page, or a dynamic buffer whose content
    changes every frame keeps that world drawing every frame. That is the
    safe side: those worlds render as they did before.

## Measured

`/dev/render-demand` (new) drives a 200-box scene on the real three
renderer exactly as `world3D.update` drives the engine's, and counts frames
drawn and draw calls over 10 s after 2 s of settling. Headless Chrome 147
on SwiftShader (software WebGL2; headless WebGPU lost its device here, so
the WebGPU backend was not measured). Ticks per 10 s are low when every
frame is drawn because software rendering limits the loop.

| Scene                                                                                                 | Frames drawn / loop ticks     | Draw calls in 10 s |
| ----------------------------------------------------------------------------------------------------- | ----------------------------- | ------------------ |
| still, render on demand                                                                               | 10 / 540 (one probe a second) | 1,920              |
| still, every frame (`?ondemand=0`)                                                                    | 80 / 80                       | 15,360             |
| instanced buffer re-uploaded every frame with the same content (`?scene=frames`, also `&mark=update`) | 10 / 544                      | 1,930              |
| playing video (`?scene=video`)                                                                        | 78 / 78                       | 15,054             |
| time-driven material (`?scene=water`)                                                                 | 72 / 72                       | 13,896             |
| moving avatar stand-in (`?scene=avatar`)                                                              | 81 / 81                       | 15,633             |

The scene draws 192 calls per frame, so on a GPU at 60 fps the every-frame
baseline is 600 frames and 115,200 draw calls per 10 s (arithmetic, not
measured); render on demand draws the 10 probe frames.

Rerun: open `/dev/render-demand?renderer=webgl&scene=still` on the dev
server; the result shows under the canvas after 12 s, and automation can
read it as JSON from `document.documentElement.dataset.renderDemand`.

Not measured: a real world (they do not load locally without database
credentials), so how often real rooms actually go idle is unknown; the
first worlds to check are a room with no water, portals or avatars in view,
visited in first person.
